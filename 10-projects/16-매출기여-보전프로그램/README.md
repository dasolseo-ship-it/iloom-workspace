# 매출기여 보전 프로그램 (온오프 보전 시스템)

## 왜 만드는가

2026년 영업지원제도 내 **매출기여** 정책(품의26-03-00266)을 자동화 시스템으로 구현.
온라인 행사로 인해 오프라인 수주가 취소될 경우, 대리점에 고객 결제액의 **5%를 자동 산출**해 지급 근거를 만드는 것이 목적.
현재는 이 정산이 수작업으로 이루어지거나 누락될 위험이 있어, 시스템화가 필요함.

---

## 정책 요약 (품의26-03-00266)

| 항목 | 내용 |
|------|------|
| 보전율 | 고객 결제액의 **5%** |
| 대상 수주 | 커넥트플러스 공지사항 등록 온라인 행사로 인한 취소건 |
| 등록 기준 | 행사 공지 **D-1일 전까지** 등록된 수주 건 |

| 예외 | 쿠시노 ≠ 쿠시노코지, 로이 ≠ 로이모노 |
| 적용 기간 | 2026-05-01 ~ 2027-05-31 |

## 프로젝트 목표 (KPI)

1. **온라인 행사마다** 오프라인 취소 건수 및 보전 금액 자동 집계
2. **매장별** 보전금 현황 대시보드 제공
3. **위탁수수료 엑셀** 형태로 자동 출력 (지급 처리 연계)

## 시스템 아키텍처 (설계 방향)

```
[데이터 소스]
  ① ERP 수주 데이터
     - 수주건명, 수주일자, 고객명, 휴대폰 뒷 4자리
     - 동(洞) 주소, 수주품목, 납기일, 대리점, 소비자가

  ② 온라인 행사 데이터 (커넥트플러스 → 구글시트로 데이터화)
     - 공지일자, 행사일자, 행사품목, 할인혜택

[매칭 로직]
  오프라인 취소건 + 온라인 주문건 → 동일 고객 특정
  키: 휴대폰 뒷 4자리 + 고객명 + 동 주소

[결과물]
  ① 대시보드 (웹 UI)
  ② 위탁수수료 엑셀 출력
```

## 핵심 기술 이슈 (미해결)

### 1. 고객 매칭 키 설계
- ERP에서 상세 주소는 더블클릭해야만 열람 가능 (개인정보 제한)
- 현실적 대안: **휴대폰 뒷 4자리 + 이름 + 동 주소** 조합
- 동명이인 리스크는 낮지만 0이 아님 → 추후 검증 필요

### 2. 취소건 정의
- ERP에서 **납기 변경**도 원수주 취소 + 신규수주 생성으로 처리됨
- 진짜 취소 vs 납기변경으로 인한 취소 구분 로직 필요
- 기준 정의 전에 실제 ERP 취소 데이터 샘플 확인 필요

### 3. 커넥트플러스 데이터 구조화
- 현재 공지사항은 이미지/텍스트 혼합 비정형 데이터
- **구글 시트**로 수동 데이터화하는 방향으로 결정 (2026-05-19 킥오프)

### 4. 5% 계산 기준
- **납기 확정 후 익월 정산** ✅ 확정 (2026-05-19)
